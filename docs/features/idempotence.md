# 草稿幂等与自愈 (Idempotence & Auto-Healing)

在内容跨平台分发工具中，**数据一致性与幂等性**是决定工具是“生产力神器”还是“灾难发生器”的核心分水岭。

文章摆渡通过「双身份映射表」、「发布状态红线防护」与「400 删稿自愈引擎」三道严密防线，彻底杜绝了草稿爆炸与数据覆盖事故。

## 🔑 双身份草稿幂等机制

许多简单搬运脚本最被人诟病的问题是：创作者在掘金微调了一个错别字或调整了排版，再次点击同步，CSDN 草稿箱里就会瞬间出现两份甚至多份一模一样的文章草稿。久而久之，草稿箱杂乱无章，难以分辨哪个才是最新版本。

文章摆渡建立了本地持久化的双身份状态映射表：

```
[掘金唯一标识 article_id] 
          │
          ▼  本地映射查询
[CSDN 草稿唯一标识 draft_id]
```

- **初次同步**：系统以新建模式保存，并将 CSDN 返回的 `draft_id` 记录至本地键值对；
- **后续同步 / 重新同步**：自动以更新（Update）模式定向覆盖对应的 `draft_id`，实现原地内容刷新；
- **排版幂等**：不会额外生成新的无用草稿碎片。

## 🛑 线上已发布博文的“红线阻断”

> [!CAUTION]
> **绝对不可触碰的红线**：绝不能为了“同步”，去盲目覆盖线上已经拥有阅读量、评论和 SEO 收录的正式博文。

如果创作者此前同步到 CSDN 草稿箱的文章已经被用户自己正式点击发布为了线上博文，随后创作者又在掘金对原博文触发了同步，如果依然按 `draft_id` 或博文 ID 盲目更新覆盖，极有可能破坏线上排版甚至导致审核被下架。

文章摆渡的防御逻辑：
1. 更新前主动向 CSDN 查询目标文章的当前发布状态；
2. 一旦检测到目标文章的 `status` 显示已进入 **“已公开发布 (Published)”** 状态；
3. 系统**立即强制阻断本次覆盖操作**，并弹出安全警示；
4. 引导创作者切换为“作为新草稿摆渡”，最大程度捍卫创作者线上已有资产的安全性。

## 🩹 400 删稿自愈引擎 (v0.6.0)


创作者经常会在 CSDN 网页端手动清理或删除测试草稿。在旧版本中，如果本地映射表依然记录着已删除的 `draft_id`，再次同步时 CSDN 服务端会返回：
```json
{ "code": 400, "message": "该文章不存在" }
```
这会导致更新操作永久报错卡死，创作者只能手动去清空插件的全部数据。

### 自愈工作原理
在 v0.6.0 中，文章摆渡构建了全自动的自愈闭环：

```
                    ┌─── [正常更新成功] ───▶ [流程结束]
                    │
[携带旧 draft_id 更新]
                    │
                    └─── [捕获 400 该文章不存在] 
                               │
                               ▼
                    [触发自愈引擎]
                      ├─ 1. 复用已成功转存的图片缓存
                      ├─ 2. 自动降级为新建草稿模式
                      ├─ 3. 将新返回的 draft_id 原地更新映射
                      └─ 4. 秒级恢复就绪态！
```

创作者全程无需任何人工干预，系统在毫秒级内即可完成自我修复。
