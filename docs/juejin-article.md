# 复制粘贴并不简单：我做了一个把掘金文章“摆渡”到 CSDN 的 Chrome 插件

我原本以为，这只是一个周末就能写完的小工具。

从掘金编辑器里拿到 Markdown，再塞进 CSDN 编辑器——听起来不过是一次跨网站的复制粘贴。

直到第一篇测试文章同步完成：图片全部裂开，代码块变成普通文本，正文顶部多出一段 CSDN 根本不认识的主题配置。更麻烦的是，登录状态、发布时机和跨域请求中的任何一个环节判断错了，都可能让“同步”变成“误操作”。

于是，这个看似简单的需求慢慢长成了一个完整的 Chrome Manifest V3 插件。我给它取名叫 **文章摆渡**。

它当前只做一件事：

> 以掘金为写作入口，把文章可靠地送到 CSDN 草稿箱，并把最终发布权留给作者。

这篇文章不只介绍怎么使用它，也想复盘一下：一个跨平台文章同步插件，真正难的到底是什么。

## 先定边界：同步不等于替你发布

做这个插件的初衷，是减少机械劳动，而不是替作者做决定。

所以第一阶段我刻意没有做“一键全平台公开发布”，而是限定了两个非常具体的场景。

### 新文章：发布掘金后，自动生成 CSDN 草稿

在掘金新文章的发布区域中，插件会增加“除掘金外还需同步”的选项。

只有同时满足两个条件，CSDN 同步才会开始：

1. 作者主动勾选同步；
2. 掘金已经确认发布成功。

第二个条件很重要。如果在点击“发布”时就立即同步，那么掘金后续的校验失败、网络错误甚至用户取消，都可能留下一篇不该出现的 CSDN 草稿。

插件因此采用了“先暂存、后确认”的方式：点击最终发布时只保存一份短期文章快照，等页面出现文章 ID 或明确的发布成功状态，再真正创建同步任务。

### 历史文章：在“更多”菜单里补一个同步入口

对于已经发布的文章，插件会在本人文章列表的“更多”菜单中增加“同步到 CSDN”。

它不会抓取渲染后的网页内容，而是根据文章 ID 找到对应的创作者草稿，读取原始 Markdown。这样可以避免从 HTML 反向转换 Markdown 时丢失代码语言、链接结构和排版信息。

为了不把按钮加到别人的文章上，历史入口只会注入到同时具有“编辑”和“删除”操作的本人文章菜单中。

如果用户尚未登录 CSDN，插件会先打开登录页，并把这次同步短暂挂起。登录完成、返回掘金后，可以继续刚才的任务，而不需要重新寻找文章。

无论哪种入口，CSDN 端都只保存草稿，不会自动公开发布。

## 我以为难点是 DOM，后来发现 DOM 只是开始

整个同步流程可以压缩成一条很短的链路：

```text
掘金文章
   ↓
读取原始 Markdown
   ↓
清洗内容与转存图片
   ↓
检查 CSDN 登录状态
   ↓
保存 CSDN 草稿
   ↓
记录结果、允许重试
```

但每个箭头后面，都藏着一个容易踩坑的边界。

## 第一个坑：content script 看得到页面，却不一定拿得到编辑器

掘金编辑器基于 CodeMirror。文章内容存在页面 JavaScript 的运行环境中，而 Chrome content script 默认运行在隔离世界里。

两边共享 DOM，但不共享 JavaScript 变量。也就是说，插件能看到编辑器节点，却不能直接访问页面内部的编辑器实例。

我的处理方式是增加一个运行在 `MAIN world` 的轻量桥接脚本：

1. 页面脚本读取标题、Markdown、草稿 ID 和当前地址；
2. 将快照临时写入 DOM 属性；
3. 通过自定义事件通知隔离环境中的 content script；
4. content script 读取后立即删除临时属性。

```text
页面运行环境（MAIN world）
        ↓ 自定义事件 + 临时 DOM 快照
扩展隔离环境（content script）
        ↓ chrome.runtime.sendMessage
后台 Service Worker
```

这里的关键不是“如何绕过隔离”，而是只建立一个很窄的数据桥：插件只读取当前任务需要的文章快照，不把整个页面环境暴露给后台。

## 第二个坑：Markdown 能复制，渲染效果却不能复制

掘金和 CSDN 都支持 Markdown，但“都支持”不代表“完全一致”。

### 主题元数据需要清理

部分 Markdown 顶部可能包含主题和代码高亮配置：

```yaml
---
theme: juejin
highlight: a11y-dark
---
```

这些配置在 CSDN 没有对应意义。如果原样同步，它们会直接出现在正文顶部。

所以内容进入适配器后的第一步，是识别并移除包含 `theme` 或 `highlight` 的 front matter，只保留真正的文章正文。

### 代码块不能靠几条正则硬转

早期版本使用简单正则将 Markdown 转成 HTML，先处理了行内代码，后处理三反引号代码块。结果是围栏内部的内容已经被改写，代码块结构自然也就坏了。

现在插件使用标准 GFM Markdown 解析流程，并保留围栏后的语言标识：

```javascript
const message = '文章已保存到 CSDN 草稿箱'
console.log(message)
```

最终同时向 CSDN 提交原始 Markdown 和解析后的 HTML。Markdown 负责后续编辑，HTML 用于保持预览和草稿内容的一致性。

这件事让我重新认识了“格式兼容”：它不是让两边像素级一致，而是确保标题层级、列表、引用、链接、图片和代码这些语义不丢失。

## 第三个坑：图片地址还在，不代表图片还能看

文章中的图片通常托管在掘金 CDN。把原地址复制到另一个平台后，可能受到防盗链、跨域策略或地址生命周期影响。

因此图片不能只“搬地址”，而要“搬文件”。

目前的处理过程是：

1. 收集正文和封面中的外链图片；
2. 由浏览器下载原图；
3. 获取 CSDN 图片上传凭证；
4. 将图片直接上传到 CSDN 图片存储；
5. 替换 Markdown 中的图片地址；
6. 所有内容准备完成后，再保存草稿。

```text
掘金 CDN 图片
      ↓ 下载
浏览器内存中的 Blob
      ↓ 上传
CSDN 图片存储
      ↓ 替换 URL
CSDN Markdown 草稿
```

如果任意一张图片处理失败，任务会明确进入失败状态并显示原因，而不是悄悄保存一篇图片全部失效的文章。

对同步工具来说，“失败得足够明显”有时比“尽量假装成功”更重要。

## 一次真实的越界：跨域规则差点影响整个 CSDN

为了让扩展后台请求 CSDN 编辑器接口，需要通过 `declarativeNetRequest` 为特定请求设置正确的 `Origin` 和 `Referer`。

最初的规则匹配范围写得太宽，把整个 `bizapi.csdn.net` 都改成了编辑器来源。这意味着，不只是插件请求，CSDN 个人中心自己发出的接口请求也可能被改写，最终触发 CORS 错误。

问题修复后，规则被收窄为：

- 只匹配插件实际使用的博客编辑接口；
- 图片上传接口使用独立规则；
- 排除所有由 CSDN 页面自身发起的请求；
- 限定资源类型为 `xmlhttprequest`。

```text
错误做法：bizapi.csdn.net/*

正确方向：
  blog-console-api/特定范围
  resource-api/特定上传接口
  + 排除 csdn.net 页面发起方
```

这是开发过程中最值得记录的一次失误。扩展权限和请求头规则不是普通配置，它们会真实改变浏览器的网络行为。规则能精确到接口，就不应该只精确到域名。

## 让同步成为一个可恢复的任务，而不是一次点击

如果同步只是一段从头执行到尾的函数，用户看到的通常只有两种结果：成功，或者“没反应”。

文章摆渡把同步拆成了可观察的状态：

```text
等待同步
  → 检查登录
  → 处理内容
  → 保存草稿
  → 同步成功

任意阶段
  → 等待登录 / 同步失败
  → 用户重新同步
```

后台 Service Worker 负责状态流转，弹窗中的历史记录则展示文章、时间、目标平台、失败原因和草稿入口。

这让“同步失败”不再是一个结束状态。网络恢复、重新登录或平台接口短暂异常之后，用户可以直接重试，而不需要重新发布掘金文章。

## 怎么安装

目前可以从源码构建，并通过 Chrome 开发者模式加载：

```bash
npm install
npm run check
npm run build
```

然后打开：

```text
chrome://extensions
```

开启“开发者模式”，点击“加载已解压的扩展程序”，选择项目生成的 `dist` 目录。

使用前，请确保在同一个 Chrome 中登录掘金和 CSDN。

## 怎么同步一篇新文章

1. 打开掘金 Markdown 编辑器并新建文章；
2. 完成标题和正文；
3. 打开发布面板；
4. 勾选 CSDN 同步选项；
5. 正常发布掘金文章；
6. 掘金确认发布成功后，插件自动生成 CSDN 草稿；
7. 在插件的同步历史中点击“查看草稿”；
8. 最后检查标签、分类、封面和排版，再决定是否在 CSDN 发布。

## 怎么同步一篇历史文章

1. 进入自己的掘金文章列表；
2. 打开目标文章的“更多”菜单；
3. 点击“同步到 CSDN”；
4. 如果尚未登录 CSDN，先完成登录；
5. 同步结束后，从插件历史记录打开 CSDN 草稿。

## 它读取了什么，又没有读取什么

插件不会读取或保存账号密码，也不会导出 Cookie。

请求中的 `credentials: include` 只是让浏览器按照权限规则携带已有登录状态，并不意味着 JavaScript 能够拿到 Cookie 内容。

文章内容和任务状态保存在当前浏览器中。正文直接发送到用户已登录的 CSDN，图片直接转存到 CSDN 图片存储，不经过开发者自己的中转服务器。

插件只在用户明确勾选或点击同步时处理文章，也只负责保存 CSDN 草稿。

## 为什么我坚持只同步到草稿箱

技术上，“保存草稿之后再自动点击发布”并不难。

但分类是否正确、标签是否合适、封面在另一个平台是否仍然成立、某些措辞是否需要针对读者调整，这些都不是代码能够可靠决定的。

跨平台分发很容易让人追求“一键完成”，但真正负责任的自动化，应该知道自己在哪一步停下来。

所以文章摆渡的终点不是“替你发出去”，而是：

> 把最机械、最容易出错的搬运工作交给插件，把最终判断留给作者。

## 写在最后：我做的不是传送门，而是一座有检查站的桥

回头看，整个插件最简单的部分，反而是把一段 Markdown 从 A 传到 B。

真正花时间的，是那些看不见的边界：

- 什么时候才算掘金真的发布成功；
- 如何从隔离环境读取编辑器数据；
- 怎样让图片不依赖原平台；
- 如何保留代码块和 Markdown 语义；
- 登录失效后怎样继续任务；
- 一条跨域规则如何只影响插件、不影响网站本身；
- 同步失败时，怎样让用户知道发生了什么。

这些问题共同决定了一个工具是“偶尔能跑的脚本”，还是“可以交给别人使用的产品”。

第一阶段的文章摆渡仍然很克制：只支持掘金到 CSDN，只保存草稿，也依赖两个平台当前的编辑器和接口。后续我会继续完善标签映射、重复同步策略、图片进度、自动化测试和开源发布流程。

但我越来越确定一件事：

> 好的同步工具，不是让内容更快地消失在更多平台里，而是让每一次搬运都可见、可控、可恢复。

如果你也做过类似的内容分发工具，或者踩过 Markdown、跨域和图片迁移的坑，欢迎交流你的实现思路。
