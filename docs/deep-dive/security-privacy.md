# 零信任隐私底座 (Security & Privacy)

技术创作者的原创博文、账号凭证是极其宝贵的个人数字资产。文章摆渡自立项之日起，便将“端侧安全与数据隐私”视作不可妥协的生命线。

## 🔒 为什么坚持「零 Cookie 权限」？

在传统浏览器插件开发中，许多开发者为了图省事，往往会在 `manifest.json` 中声明：
```json
{
  "permissions": ["cookies", "<all_urls>"]
}
```
这意味着该插件在技术上具备读取用户在所有网站（包括网银、社交媒体、邮箱）的 Cookie 凭证的能力，存在巨大的信任风险。

### 文章摆渡的实践
- **拒绝声明 `cookies` 权限**：插件完全无法直接触碰浏览器的 Cookie 存储区；
- **复用原生浏览器上下文**：利用 Chrome 原生的 `declarativeNetRequestWithHostAccess` 与主机白名单，仅在用户触发对掘金、CSDN 的官方接口请求时，由浏览器底层自然携带登录态完成鉴权；
- **从根源杜绝数据泄露**：即使插件代码遭遇极端注入攻击，攻击者也无法通过插件 API 窃取到用户的任何身份 Cookie。

## 💻 纯端侧闭环 (Local-First Computing)

市面上不少同步服务要求创作者“先将文章提交到其云端服务器，再由服务器分发到各平台”。这种集中式架构存在三个致命隐患：
1. **云端单点故障**：第三方服务器宕机导致工具瘫痪；
2. **知识资产泄露**：未公开的技术底稿或商业机密被第三方云端留存；
3. **账号风控关联**：多位创作者共用同一云端 IP 发送请求，极易触发目标平台防刷风控导致封号。

**文章摆渡采用 100% 本地端侧架构**：
- 没有中间云服务器，所有 Markdown 词法分析、图床搬运全在创作者本地机器完成；
- 请求直接从创作者的本地网络 IP 发出，平台判定为创作者本人的正常发文交互，安全合规。

## 🛡️ Chrome Storage 存储瘦身防爆仓策略


Chrome 扩展提供的本地持久化存储 `chrome.storage.local` 具备默认 **10MB 的物理配额限制**。

若每篇同步文章都将全量 Markdown 正文完整保存在本地任务历史中，一篇技术长文占用 50KB ~ 100KB，当同步记录累计到 100~200 篇时，就会直接**冲破 10MB 配额导致 `QUOTA_BYTES` 异常崩溃**。

### 文章摆渡的瘦身治理方案
1. **持久化剥离大文本**：在任务落盘持久化时，主动剔除巨大的 `markdown` 正文字符串，仅保留标题、时间、状态与文章 ID 等轻量元数据；
2. **按需双路径拉取**：若后续用户需要“重试”或“重新摆渡”，系统根据记录中的 ID 动态调用掘金官方 Draft 接口拉取最新原文；
3. **数据吞吐倍增**：使得本地存储空间占用降低了 95% 以上，轻松容纳数万条同步历史记录而永远不会爆仓。
